# M2 walkthrough — vehicle layer

## What was built

M2 is the code that talks to an OBD adapter, plus the guarantee that it can only read. A request starts as a string such as `"010C"`. The allowlist turns it into an `AllowedCommand` or refuses it; the TCP transport writes it and returns raw bytes; the ELM327 layer turns the bytes into CAN frames and joins multi-frame replies; the parsers turn the result into typed values. `ELM327Vehicle` wraps this behind the `Vehicle` protocol, which has no method that writes.

Three terms: a **PID** is one readable value (engine speed is PID `0C` of mode `01`). An **ECU** is a computer in the car, answering under a CAN ID such as `7E8` (the engine). **ISO-TP** cuts a reply longer than 7 bytes into several CAN frames, each starting with a control byte, the **PCI**.

## How data flows

```text
"010C" -> allowlist.parse -> AllowedCommand -> TcpTransport.send -> raw bytes
       -> clean_lines -> parse_reply (one CanFrame per line) -> reassemble (bytes per ECU)
       -> ELM327Vehicle._request (keeps positive replies) -> parsers.decode_pid -> Reading
```

Read first:

1. [vehicle/allowlist.py](../../src/obdient/vehicle/allowlist.py). The whole read-only claim is `_classify`, about 25 lines.
2. [vehicle/elm327.py](../../src/obdient/vehicle/elm327.py). `clean_lines`, `parse_reply` and `reassemble` are pure functions; try them in a REPL on the strings in `tests/fixtures/elm_responses/handwritten.json`. Then `_request`, which every `Vehicle` method goes through.
3. [vehicle/parsers.py](../../src/obdient/vehicle/parsers.py) with [pids.py](../../src/obdient/vehicle/pids.py) beside it: the bit layouts and formulas.

## Decisions SPEC and PLAN did not dictate

| Decision | Alternative rejected |
| --- | --- |
| `AllowedCommand` re-runs the grammar in `__post_init__` and in `.wire`. | Trusting the private token alone; Python cannot hide it. |
| `decode_pid` rounds to the PID's `decimals`. | Exact values, rounded later. Rounding once keeps readings, simulator and evidence identical. |
| `decode_dtcs` accepts replies with or without a count byte. | SPEC's form only. See "Surprises". |
| `_request` returns `(payloads, error)`; the caller decides whether to record. | Recording inside. `NO DATA` for a code request means "none". |
| A failed multi-PID request records nothing; each PID is then asked alone. | Recording the group failure too, which double-counts. |
| An ECU's refusal (`7F ..`) of a code request is recorded; the adapter's plain `NO DATA` is not. | Treating both as "no codes". |
| The freeze frame asks only for PIDs with a decoder, and follows the support bitmap past `020000`. | SPEC's literal "each supported PID in the table": about 50 requests for values we cannot decode. |
| Headers-off replies get PCI bytes rebuilt, so one `reassemble` serves both formats. | A second path used only by tests. |
| `ElmReply.detail`, and public `ecus` and `timeout_s` on `ELM327Vehicle`. | SPEC's exact shapes. M3's collector needs the ECU list. |
| Refusals show `repr()` of the command. | Raw text, which puts a real carriage return in a log line. |
| A dropped connection is recorded as `ADAPTER_ERROR`; an `ATZ` timeout says "Adapter not responding". | A new error kind; SPEC's "did not identify itself", which fits a wrong reply, not silence. |
| Added `tests/unit/test_elm327.py` with a scripted transport. | Testing setup and fallbacks only through the slow emulator. |

## One example, end to end

`vehicle.read_pids(["010C"])` against the emulator:

1. `"010C"` is in `supported_pids()`, so it may be sent.
2. `allowlist.parse("010C")`: legal characters, not an AT command, valid hex, first byte `01` is a read mode, and the text matches `01(?:[0-9A-F]{2}){1,6}`. Result: `AllowedCommand(text="010C", kind="obd", mode=1)`.
3. `TcpTransport.send` writes `command.wire`: the 5 bytes `30 31 30 43 0D` (`010C` and a carriage return). It reads until `>`.
4. The emulator answers `7E804410C145F\r\r>`. The transport returns everything before the prompt.
5. `clean_lines` gives `["7E804410C145F"]`.
6. `parse_reply`: ECU `7E8`, data `04 41 0C 14 5F`.
7. `reassemble`: PCI `04` is a single frame of 4 bytes. Payload `41 0C 14 5F`.
8. `_request`: `41` is mode `01` plus `0x40`, a positive reply. `7F` would be a refusal.
9. `_read_raw`: `0C` is the PID we asked for; the data is `14 5F`.
10. `decode_pid`: (0x14 × 256 + 0x5F) / 4 = 5215 / 4 = 1303.75, rounded to 0 decimals.
11. `Reading(pid="010C", name="rpm", value=1304.0, unit="rpm", ecu="7E8", raw="145F", ...)`.

Given `"04"`, step 2 raises `ForbiddenCommandError` and nothing reaches step 3.

## Surprises and things to double-check

- **The emulator's trouble-code replies disagree with SPEC.** For one stored code it sends `43 01 71`; SPEC §4.5 says `43 01 01 71`, with a count byte. The decoder accepts both, told apart by length. I believe the count-byte form is what the GTI sends, but that is from memory of the standard. Logged as V15 in SPEC §16 for M8.
- **The review subagent found five defects, all fixed with tests** (end of `test_elm327.py`): `since_clear()` could raise on a short reply; a "response pending" frame (`7F .. 78`) hid the real answer; an ECU's refusal of a code request was read as "no codes"; setup accepted any reply containing `OK`; the `0100` search was retried, doubling the 10 s wait. The second and third could each have dropped a stored code silently.
- **Length-only PID sizes are from memory** of the published J1979 table (`_LENGTH_ONLY` in `pids.py`). A wrong length would mis-split a multi-PID reply and could give a wrong value without an error. V5 stays open.
- **Formulas were not cross-checked against OBDex**: `data/obdex/` is not in the repo yet. `test_pids.py` uses hand arithmetic only.
- **Late replies after a timeout.** The next `send` discards bytes that have already arrived, but a reply landing during the next request would be read as its answer. The PID-echo check catches this for mode 01 only. Watch for it over BLE in M8.
- **The emulator's car has no freeze frame**, so that path is tested only with the scripted transport.
- The "nothing was cleared" proof has a control test that sends a raw `04` from the test's own socket and checks the emulator's counter flips. Without it the main assertion could pass vacuously.
- The emulator test still uses a hand-written read sequence; M3 swaps in `collect()`.

## Quiz

1. `parse("0101010101010101")` is refused. With which reason, and why not `mode_not_permitted`?
2. A reply line reads `7E8 10 14 49 02 01 57 56 57`. What do `10 14` mean, and how many more frames follow?
3. ECUs `7E9` and `7E8` both answer `010C`. Which value does `read_pids` return?
4. `read_dtcs()` gets `NO DATA` for `0A`, then `7F 03 11` for `03`. Which one records a `ReadError`?
5. Why does `TcpTransport.send` check `isinstance(command, AllowedCommand)` when the type hint says so already?

### Answers (spoilers)

1. `bad_shape`. Mode `01` is permitted, but the request names 7 PIDs and the limit is 6.
2. High nibble `1` marks a first frame; the other 12 bits (`0x014`) say the payload is 20 bytes. This frame carries 6 and each later one 7, so 2 more.
3. The one from `7E8`: the lowest responding ID is taken as the engine ECU. `7E9` is only remembered in `vehicle.ecus`.
4. Only the `7F`. `NO DATA` means "no codes of that kind"; `7F` means the ECU refused, and the answer is unknown.
5. Type hints are not enforced at runtime. The check keeps "only allowlisted bytes are written" true for a caller that ignores the type checker.
