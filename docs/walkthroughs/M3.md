# M3 walkthrough — simulator and scenarios

## What was built

M3 adds a fake car and the first end-to-end command. A **scenario** is a YAML file describing one broken car (codes, sensor values, what the owner says) plus the diagnosis the graders will expect. `ScenarioSimulator` turns a scenario into a `Vehicle`, the same interface the real adapter code implements. `collect()` reads any `Vehicle` once, in a fixed order, and returns a `Snapshot`. `Database` stores it in SQLite. `userio.py` holds the intake questions and the fixed safety prompts. `obdient scan` ties these together. Ten scenario files were written from sources you approved.

## How data flows

```text
scenarios/s01_pcv_lean.yaml -> load_scenario -> Scenario -> ScenarioSimulator (a Vehicle)
   -> collect(): connect, supported_pids, vin, status, read_dtcs, freeze_frame, since_clear,
                 then 3 x read_pids per condition, drain_errors, close
   -> Snapshot -> Database.save_snapshot -> ~/.obdient/obdient.db
```

Read first:

1. [vehicle/collector.py](../../src/obdient/vehicle/collector.py). `collect()` is one function, and it is the only code that decides what a Snapshot contains. Everything from M4 on consumes its output.
2. [schemas/scenario.py](../../src/obdient/schemas/scenario.py). The `Scenario` model and its `_consistent` validator are the rules a scenario file must obey. Read `scenarios/s01_pcv_lean.yaml` beside it.
3. [vehicle/simulator.py](../../src/obdient/vehicle/simulator.py). Short, and it shows what the `Vehicle` protocol means without any OBD byte handling.

## Decisions SPEC and PLAN did not dictate

| Decision | Alternative rejected |
| --- | --- |
| The simulator's `captured_at` is a constant (`SIMULATED_EPOCH`, 2026-01-01). `snapshot_id` stays random. | Wall-clock time, which breaks "two runs give identical JSON". A fixed ID, which makes the second `scan --scenario s01` fail on insert. |
| `latest_snapshot()` returns the last one stored. | Ordering by `captured_at`: every simulator scan has the same one. |
| `ConditionPrompter` gained `release()`, called even if reading fails. | Printing "Release the pedal." from the collector, which should not print. SPEC updated. |
| In `scan`, a real car is read first and the intake questions come after. | Asking first. The flashing-light question needs to know whether the car reports its MIL on. |
| A malformed VIN from the car is dropped and recorded as a read error. | Raising. One bad reply should not lose the scan. |
| A simulator given explicit `--condition` flags captures only those. | Ignoring the flags. SPEC covers only the default. |
| `conditions_captured` lists each label once, ordered by last capture. | Repeating `unknown` when two phases are relabelled. |
| Scenario errors list up to five problems. | Only the first. Pydantic reports a union's first branch, which hid the real cause. |
| Scenario PID values must be real numbers, and raw PID keys must have a decoder. | Pydantic's coercion, which accepts `true` and `"12"`. SPEC updated. |
| The 2018 scenarios other than s01 do not define `maf_gs`. | Giving every file a MAF value. That car has no MAF sensor; s01 keeps it because SPEC fixes that file (V16). |

## One example, end to end

`uv run obdient scan --scenario s01`:

1. `cli.scan` sees `--scenario`, so the source is the simulator. `resolve_scenario("s01", scenarios/)` finds the one file whose name starts with `s01`.
2. `load_scenario` parses the YAML and validates it: `rpm`, `ltft_b1` and the rest are known PID names, the freeze-frame trigger P0171 is a stored code, and `conditions` contains `initial_condition` (`idle`).
3. `scenario.build_user_report()` makes the `UserReport`.
4. `ScenarioSimulator(scenario)` converts names to PID identifiers: `idle` becomes `{010C: 780, 0107: 19.5, 0106: 6.2, 0110: 2.4, 0105: 90, 010D: 0}`.
5. `collect()` calls `connect()`, then `supported_pids()`: the six PIDs above plus `0101` (status) and `0130`, `0131` (warm-ups and distance since clear).
6. `vin()`, `status()` (MIL on, 1 code, 7 monitors supported and complete), `read_dtcs()` (P0171 stored and permanent), `freeze_frame()`, `since_clear()` (45 warm-ups, 820 km).
7. The default condition list means "whatever the scenario defines, initial one last": `[hold_2500, idle]`.
8. Phase 1: `set_condition(hold_2500)`, then three `read_pids` calls for the six PIDs. Each reading is stamped `hold_2500` with times 0.5 s, 1.0 s and 1.5 s after the epoch. Mean rpm is 2500 and speed 0, so the label stands.
9. Phase 2: `set_condition(idle)`, three more reads at 2.0 s to 3.0 s, stamped `idle`. Mean rpm 780: the label stands.
10. `drain_errors()` returns nothing; `close()` runs in `finally`.
11. The Snapshot has 36 readings (2 conditions × 3 samples × 6 PIDs) and `conditions_captured = [hold_2500, idle]`. Idle is last, so it is the "current" condition.
12. `Database.save_snapshot` inserts one row. The summary is printed with the VIN masked.

M4 will compute total fuel trim from these: +25.7 % at idle and +7.5 % at 2,500 rpm.

## Surprises and things to double-check

- **The 2018 GTI has no MAF sensor**, so the PRD's scenario 2 could not happen on it. s02 is a 2013 GTI (SPEC X12). Whether your car reports `maf_gs` at all is open until M8 (V16).
- **Expected escalations are provisional.** `P1_limp_mode_code` depends on OBDex flags I cannot see yet. s05 assumes P0299 is flagged; s10 may gain `prompt`.
- **s04 has no source for its pairing.** The leak is well sourced and so is the warranty bulletin; nothing pairs P0128 with a leak.
- **s06, s07, s08 and s10 cite OBDex entries I have not read.** Check them when `data/obdex/` arrives.
- **`nhtsa: {fixture: gti_2018}` points at a directory that does not exist yet.** Nothing reads it until M4.
- **The review subagent found eight small defects, all fixed with tests.** The worst: `--symptoms` over 2,000 characters stored a Snapshot that could not be read back. Others: YAML reads an unquoted `0105` key as the number 69; `rpm: yes` loaded as 1 rpm; a failed collect left the simulator in the wrong condition.

## Quiz

1. s01 defines `idle` and `hold_2500`, in that order. Why does the Snapshot list `hold_2500` first?
2. A scan declared `--condition idle` averages 1,700 rpm. What happens to its readings?
3. Why is a scenario's VIN `WVWZZZ_FIXTURE` accepted when `--vin TOOSHORT` is refused?
4. You run `scan --scenario s01` twice. Which Snapshot fields differ?
5. A scenario's freeze frame has `load_pct` but its `idle` condition does not. What appears in the Snapshot?

### Answers (spoilers)

1. The collector captures the initial condition last, so the final readings are the car's "current" state.
2. All readings of that phase are relabelled `unknown`, and one `CONDITION MISMATCH` read error records why.
3. Scenario VINs are synthetic and exempt from the 17-character pattern (`vin_source="scenario"`); a user override must match it.
4. Only `snapshot_id`. Times come from the simulator's fixed clock.
5. `load_pct` counts as supported, so each of the three idle reads records a `NO DATA` error for `0104`.
